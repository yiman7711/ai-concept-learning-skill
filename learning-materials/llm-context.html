大模型的上下文（Context）精讲

个人学习卡片 · 由 concept-mastery Skill 生成 · 学习日期 2026-09-09 · 领域：LLM 原理

0. 一句话定位

上下文本体上指模型一次推理时"能看到"的全部输入信息；而"上下文窗口（Context Window）"是这个"能看到"的容量上限（以 token 计）——它决定模型能否"记得"多早以前说过的话、多长的一段文档，本质是模型一段有限的工作记忆。

1. 学习目标

  • 我能区分"上下文"与"上下文窗口"这两个词，并说清 token 计量的意义。
  • 我能解释为什么模型在长对话里会"忘记"开头内容。
  • 我能说明"上下文窗口≠模型真的全部用得上"，理解"大海捞针"测试的用意。
  • 我能把上下文管理（截断/摘要/RAG）用于设计更稳的提示与 Agent。

2. 核心问题

  1. 模型到底"记得"什么？它有没有长期记忆？
  2. 为什么聊久了它会忘掉最开始的要求？
  3. 上下文窗口很大，就代表它都处理得很好吗？
  4. 工程上如何"管理"有限的上下文（截断、摘要、外挂检索）？

3. 结构化解释

3.1 我的理解

把上下文想成模型面前的一张固定大小的"工作台/黑板"：我写的问题、模型生成的回答、以及之前几轮对话，都被切成 token 摆在这张黑板上。黑板尺寸有限（例如 128K token），一旦写满，为了记下新内容，最早写在角落的话就会被"擦掉"。所以模型不是不记得，而是它每次只能基于"当前黑板上还剩的内容"来续写——更早的早已不在它的视野里。

让我最受触动的一点是：模型没有"想记住"的主观意图，也没有独立的长期记忆库。所谓"记忆"不过是上下文窗口里此刻仍保留的那部分文本。这也是为什么在多轮 Agent 对话里，系统要把关键状态反复写回上下文、或用外部数据库（RAG、向量库）把"历史"捞回来——因为它真正能"看见"的只有窗口内那一块。

3.2 核心机制与组成

概念英文含义
上下文Context模型单次推理可参考的全部输入（历史 + 当前提示 + 已生成内容）
上下文窗口Context Window单次能处理的最大 token 数上限
Token / 词元Token模型处理文本的最小单元（中约 1.5–2 字 / token）
注意力机制Self-Attention让模型在序列内各 token 间建立关联；计算随长度近似平方增长
位置编码Positional Encoding (RoPE 等)让模型区分 token 先后顺序，关系到长文本能否"用满"窗口

关键边界——"窗口大小"和"有效利用"是两回事：

即便某模型名义支持百万 token，它对窗口中部与后部信息的"关注质量"也可能下降。业界用"大海捞针（needle-in-a-haystack）"这类基准来检验：把一句关键事实埋进很长的文档里，看模型还能不能准确找出来。结果是，很多模型的有效上下文明显小于标称上下文。

3.3 关键术语

  • Context / 上下文：模型此刻参考的文本集合。
  • Context Window / 上下文窗口：token 容量上限。
  • Token / 词元：文本的切分最小单元，也是计费单位。
  • Input / Output tokens：一次请求中模型读入与产出的 token。
  • Max output tokens：单次输出上限（可独立于窗口配置）。
  • RAG / 检索增强：把相关片段检索出来塞进上下文，而不塞全部历史。

4. 应用场景示例

场景写一个"多轮客服 Agent"时如何不丢关键信息

  1. 用户先说了订单号与诉求，又聊了很多句无关内容。若全塞进上下文，窗口很快满，最早的"订单号"可能被挤掉。
  2. 工程做法：每次轮次只把"系统摘要（订单号+用户诉求+已做步骤）"重新写回上下文，而不是无脑拼接全部原始聊天。
  3. 再叠加 RAG：订单详情等长资料存在外部，只在需要时检索关键片段放入上下文。
  4. 结果：模型始终在有限窗口内保有最关键的信息，既省 token 又不易"失忆"。

这也回答了开篇问题：真正可靠的"记忆"要靠工程化上下文管理（摘要、截断、检索），而不是指望模型自己记住一切。

5. 概念辨析与使用边界

对比维度上下文窗口 Context Window易混淆对象
vs. 上下文长度 Context Length实际预测时模型考虑的输入序列长度，≤ 架构上限模型架构能处理的理论上限（能力边界）
vs. 长期记忆 / 训练知识会话级、短期的"工作记忆"，用完即失训练时学到、长期驻留模型参数里的知识
vs. "窗口越大=越强"还需考虑有效利用与算力成本盲目堆窗口会带来平方级计算开销与"中间信息丢失"

使用边界提醒：不要把"把它全塞进上下文"当作唯一解法。窗口越大，单次算力与费用越高；且超长输入可能触发位置编码外推导致的中间遗忘。要按信息优先级取舍——放不下就做摘要或外挂检索。

6. 自测问题

Q1：模型在很长的多轮对话里"忘记"开头，最直接原因是什么？

参考答案：早期内容已超出上下文窗口、被新内容"挤掉"，不再参与本次生成——并非模型"故意遗忘"，而是它只能基于窗口内现存文本续写。

Q2：上下文窗口的计量单位是什么？它包含哪些内容？

参考答案：以 token 数计量。包含当前提示输入、已生成输出，多轮时通常还有最近几轮历史。

Q3："标称窗口很大"是否等于"都处理得很好"？

参考答案：不一定。受注意力机制与位置编码影响，模型对长文中间/后段信息可能关注不足，"有效上下文"常小于标称值，"大海捞针"测试即用于检验。

Q4：若历史太长放不进窗口，有哪些工程手段？

参考答案：截断最旧的、把历史压缩成系统摘要、用 RAG/向量检索只注入关键片段、或将长文档分段处理。
