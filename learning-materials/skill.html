Skill（技能）精讲

个人学习卡片 · 由 concept-mastery Skill 生成 · 学习日期 2026-09-09 · 领域：AI 工程

0. 一句话定位

Skill 是一种把"做某类任务的方法与知识"打包成可复用文件（SKILL.md + 脚本/资料）的能力单元；它被放在文件系统里，当任务相关时才被按需加载，从而把个人/团队的一次性经验沉淀成可重复调用、稳定可靠的"专长"。

1. 学习目标

  • 我能说出 Skill 由哪些部分组成，以及 SKILL.md 里必须写的字段（name / description）。
  • 我能解释"渐进式披露"如何帮模型省上下文。
  • 我能区分 Skill 与 Prompt、与 Project 的关系，判断何时该把提示词沉淀成 Skill。
  • 我能亲手写一个结构规范、能复用、可自检的自定义 Skill。

2. 核心问题

  1. Skill 和一段"写得很好的提示词"到底有什么区别？
  2. 为什么 Skill 要做成"基于文件系统的目录 + 分层加载"？
  3. Skill 如何把"个人会做、但要反复解释"的任务知识沉淀下来？
  4. 写一个 Skill 时，如何保证它可靠、安全、可维护？

3. 结构化解释

3.1 我的理解

把 Skill 想成一份"给新同事的入职交接手册"：里面不只有"该做什么"，还有"我惯用的方法、最佳实践、样例、以及别踩的坑"。跟对话里临时说一句"帮我按 XX 格式做"不同，Skill 把这些写成了独立文件，可以跨对话复用，下次一提相关任务它就自动按这套规矩干活。

让我最有感触的设计是"渐进式披露"（progressive disclosure）：平时模型只读每个 Skill 几十个 token 的 name+description（用来判断何时触发），直到真用到某个 Skill 时才去读它完整的 SKILL.md，再必要时才去读脚本/资料。这样装了再多的 Skill 也不会白白挤占上下文窗口——正好呼应了我上一张卡片"上下文"里学到的痛点。

3.2 核心机制与组成

一个 Skill 就是一个目录，典型结构：

my-skill/
├── SKILL.md            # 主说明：YAML 元数据 + 操作指引
├── REFERENCE.md        # (可选) 更细的参考/规范
└── scripts/
    └── tool.py         # (可选) 确定性执行的脚本/工具

SKILL.md 顶部必须包含 YAML 元数据：

---
name: my-skill
description: 它做什么 + 何时该用（用于触发匹配）
---
# 正文：清晰的分步指引、样例、最佳实践…

加载分三层、时机不同，正是它省上下文的关键：

层级何时加载成本内容
Level 1 · 元数据启动时常驻约 100 token/个name + description（用于判断是否触发）
Level 2 · 指令触发后才读<5K tokenSKILL.md 正文，方法与指引
Level 3 · 资源/脚本按需读取/执行用前为 0参考文件、脚本（只把执行结果带回上下文）

3.3 关键术语

  • Skill / 技能：可复用的、基于文件系统的能力包。
  • SKILL.md：含 YAML 元数据 + 操作指引的核心文件。
  • YAML frontmatter / 元数据：文件顶部 --- 之间的字段（name/description 等）。
  • Progressive disclosure / 渐进式披露：按需分层加载，省上下文。
  • Agent Skills：Anthropic 提出的"装进 Agent、按任务自动使用"的 Skill 方案。
  • skill-creator：用于辅助生成规范 Skill 结构的工具/技能。

4. 应用场景示例

场景把"整理会议纪要"沉淀成一个 Skill

  1. 发现问题：我每周都要让 AI 把会议记录整理成"待办+决策+风险"三段式，每次都重复解释格式。
  2. 沉淀为 Skill：建目录 meeting-notes/，写 SKILL.md，在 description 写清"当用户上传会议记录、要求整理纪要时使用"，正文写清三段式模板、语气规范、以及输出示例。
  3. 复用：以后直接说"整理这份纪要"，模型读 description 判断触发 → 读 SKILL.md → 按既定格式稳定产出，不用再教它一遍。
  4. 可组合：若还想要"纪要转行动项追踪表"，可以再加一个配套 Skill 或脚本，做多步流程。

这正是作业里我写 concept-mastery Skill 的思路：把"学新概念要包含哪些部分、来源怎么核查、怎么自检"这套我自己的方法固化下来，之后学任何新概念都能调用同一套高质量流程，而不是每次从零写提示。

5. 概念辨析与使用边界

对比维度Skill易混淆对象
vs. Prompt（提示词）独立文件、跨对话持久复用、按需加载会话内一次性、易失、需反复输入
vs. Project（项目/上下文）针对某类任务的方法包，可在不同会话触发绑在某项目/会话上下文的长期资料
vs. Tool（工具）提供"怎么做的方法知识"（偏指令/流程）提供可执行的原子能力（偏函数/API）
vs. MCP（服务连接）本地能力与知识包外部工具/数据连接协议

使用边界与安全提醒：Skill 本质是给模型"授予新能力"，等于给模型装了可执行指令与代码。只使用可信来源（自己写的、或官方/可信渠道的）。写好后要通读一遍、检查其中有没有可疑的网络请求或越权操作。判断标准：若一段提示词你在多个会话里反复重复，就值得沉淀成 Skill；否则别过度封装。

6. 自测问题

Q1：SKILL.md 顶部必须写哪两个字段？它们各起什么作用？

参考答案：name（Skill 名称）与 description（说明做什么 + 何时触发）。description 是模型匹配请求、决定是否加载该 Skill 的依据。

Q2：为什么 Skill 采用"渐进式披露"分层加载？

参考答案：平时只占少量 token（元数据），触发后才读完整指令、按需读脚本/资源，从而避免把大量 Skill 内容一次性塞进有限的上下文窗口。

Q3：什么时候"该把提示词升级成 Skill"？

参考答案：当同一段规范/流程需要在多个会话反复使用、想保证输出一致性时（例如品牌格式、分析方法、文档模板），就该固化成一个 Skill。

Q4：使用第三方 Skill 前要注意什么？

参考答案：审查 SKILL.md 及其脚本/资源，警惕可疑的外部网络请求、异常文件访问或越权操作；只用可信来源的 Skill。
